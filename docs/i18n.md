# Internationalization (English / Arabic)

The site is served in two languages with [next-intl](https://next-intl.dev) v4:

| Locale  | URL prefix | Direction | Default |
| ------- | ---------- | --------- | ------- |
| English | `/en`      | LTR       | ✓       |
| Arabic  | `/ar`      | RTL       |         |

Every page is statically prerendered for both locales (16 pages: 8 routes × 2).
A request without a prefix (`/`, `/about`) is redirected to a locale chosen from
the `NEXT_LOCALE` cookie, then the browser's `Accept-Language`, then English.

---

## How it fits together

```
proxy.ts                        Locale detection + redirects (Next 16's middleware)
next.config.ts                  Registers the next-intl plugin → shared/i18n/request.ts
messages/
  en.json                       English copy (source of truth for message types)
  ar.json                       Arabic copy — must have exactly the same keys
shared/i18n/
  routing.ts                    Locales, default locale, getLocaleDirection()
  navigation.ts                 Locale-aware Link, usePathname, useRouter, redirect
  request.ts                    Loads the messages for the current request
  page-locale.ts                initPageLocale(): validates [locale], enables static rendering
  next-intl.d.ts                Types every t("…") key against messages/en.json
shared/lib/routes.ts            The single map of page paths (nav, footer, header)
shared/components/locale-switcher.tsx   Header link to the same page in the other language
app/[locale]/                   All routes live under the locale segment
  layout.tsx                    <html lang dir>, fonts, NextIntlClientProvider
```

### Pages

Every `page.tsx` and the layout start with:

```tsx
export default async function ServicesPage({ params }: PageProps<"/[locale]/services">) {
  await initPageLocale(params) // 404s on an unknown locale, keeps the page static
  …
}
```

`PageProps` and `LayoutProps` are global helpers that Next generates into
`.next/types`. On a fresh clone, run `npx next typegen` (or `dev`/`build`) once
before `npm run typecheck`.

### Components

Server and client components both use `useTranslations`, declared first in the
component per the house order (`// Translation`):

```tsx
const t = useTranslations("ServiceDivisions")
t("title")
t(`divisions.${division.key}.title`)
t.rich("envelopeNote", { label: (chunks) => <span>{chunks}</span> })
```

Keys are **type-checked**: a missing or misspelt key fails `npm run typecheck`
and the build.

### Data files

Feature `data/*.ts` files no longer hold English copy. They hold **message keys**
plus everything that is not language-specific (ids, icons, numbers, years,
hrefs). Key types are derived from the messages, so the data can't point at a
key that doesn't exist:

```ts
type PrincipleKey = keyof Messages["AboutPrinciples"]["items"]

const principles: { key: PrincipleKey; icon: LucideIcon }[] = [
  { key: "integrity", icon: Shield },
  …
]
```

## Message structure

One namespace per component or section (PascalCase), camelCase keys inside.
Section copy is flat; repeated items are grouped under a plural key
(`items`, `stats`, `tags`, `sectors` …). Long plain-string lists that are shared
or referenced from several places get their own flat namespace
(`DivisionCapabilities`, `ClientNames`).

| Namespace                                                                   | Used by                                          |
| --------------------------------------------------------------------------- | ------------------------------------------------ |
| `Header`, `Navigation`, `ThemeToggle`, `LocaleSwitcher`, `Footer`           | Site chrome                                      |
| `PageHero`                                                                  | Hero banner on every inner page                  |
| `Units`                                                                     | `+` and `m` / `م` suffixes on counted-up figures |
| `HomeHero`, `HomeClients`, `HomeTrackRecord`, `HomeEdge`                    | Home                                             |
| `AboutIntro`, `AboutPrinciples`, `AboutMission`                             | About                                            |
| `ServiceDivisions`, `DivisionCapabilities`, `ServiceFacilities`             | Services                                         |
| `ProjectsFeatured`, `ProjectsCompleted`, `ProjectStats`                     | Projects                                         |
| `ClientSectors`, `StrategicClients`, `ClientOrganizations`, `ClientNames`   | Clients                                          |
| `ContactIntro`, `ContactDetails`, `InquiryForm`                             | Contact                                          |
| `QualityCredentials`, `QualityStandards`, `QualityProcess`, `QualityVision` | Quality                                          |

Messages use ICU syntax: `{count}` placeholders, and tags such as `<br></br>`,
`<num>…</num>` or `<label>…</label>` rendered through `t.rich`.

## Common tasks

### Change or add a piece of text

1. Add or edit the key in **both** `messages/en.json` and `messages/ar.json`.
2. Use it with `t("key")`. The key autocompletes and is type-checked.

### Add a new page

1. Create `app/[locale]/(pages)/<route>/page.tsx` and call `initPageLocale(params)`.
2. Add the path to `ROUTES` in `shared/lib/routes.ts` and its label to `Navigation`.
3. If it has a hero, add its key to `PAGE_HERO_KEYS` (and to
   `DESCRIBED_PAGE_HERO_KEYS` if it has a lead) and the copy under `PageHero`.
4. Internal links must use `Link` from `@/shared/i18n/navigation`, **not**
   `next/link`, so they keep the current locale. (`next/link` is still fine for
   `tel:` and `mailto:`.)

### Add a new language

1. Add it to `locales` in `shared/i18n/routing.ts` (and to `RTL_LOCALES` if it is
   right-to-left).
2. Create `messages/<locale>.json` with every key from `en.json`.
3. `LocaleSwitcher` currently toggles between two locales. With three or more it
   needs to become a menu.

## Right-to-left (Arabic)

`<html dir="rtl" lang="ar">` flips the layout. Components follow these rules:

- **Logical utilities only:** `ps-/pe-`, `ms-/me-`, `start-/end-`, `text-start/end`.
  No `left-/right-` or `pl-/pr-` for anything that should mirror.
  Physical values remain only where the code measures physical offsets (the
  hero headline caret uses `offsetLeft`).
- **Direction-aware motion:** the hero headline, the facility list and the page
  title wipe read `getLocaleDirection(locale)` (or the computed `direction`) to
  enter from the reading side.
- **No per-letter splitting of Arabic:** Arabic letters join, so wrapping each
  letter in an `inline-block` breaks the word. `HeroHeadline` animates whole
  words in RTL and single letters in LTR.
- **No letter-spacing on Arabic:** the `type-label-*` and `type-eyebrow-*`
  utilities reset tracking under `:lang(ar)`; inline `tracking-[…]` classes add
  `rtl:tracking-normal`.
- **No faux italic:** quotes add `rtl:font-sans rtl:not-italic`.
- **Phone numbers and emails stay LTR** (`dir="ltr"`) so `+966 …` doesn't reorder.
  The shared `Input` applies `dir` to its own wrapper so the status icon and the
  padding reserved for it stay on the same side.
- **Mobile menu** opens from the left in RTL. `SheetContent` takes a translated
  `closeLabel`.
- Digits stay Western (0–9) in both languages, as is usual on Saudi business sites.

## Arabic font

DM Sans, Sora and JetBrains Mono have no Arabic glyphs. **IBM Plex Sans Arabic**
(OFL, 400–700, self-hosted in `app/fonts/` like the other faces) is added as the
fallback in every font stack in `globals.css`:

```css
font-family: var(--font-dm-sans), var(--font-plex-arabic), sans-serif;
```

Latin text keeps its original face and Arabic text falls through to Plex. The
font is declared with an Arabic `unicode-range` and `preload: false`, so English
pages don't download it. The one exception is the "العربية" switcher label, which
fetches a single weight (500).
